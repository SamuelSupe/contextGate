# Publish an existing query as an Agent tool

[简体中文](query-publishing.zh-CN.md) · [Getting started](getting-started.md)

Use **Home → New query** when you already have a working read query or a fixed HTTP read operation. ContextGate reuses its existing semantic templates, source authorization and query engine. You do not need an ontology or a new access-control model.

1. **Choose source.** Select an existing source or connect a new one. New sources in this flow recommend **Templates only**; inspect the access selector before saving. Existing modes are preserved. Review connectivity, engine protection and account-permission evidence separately. “Not verified” remains unverified.
2. **Provide query.** Paste native query text and put parameter values in **Fixed parameter values and query options**, or edit the complete query JSON. You can also choose **Create query tool from this query** in the native preview. HTTP sources can copy a configured operation and its parameter contract. No SQL literals are automatically converted into placeholders.
3. **Purpose and inputs.** Provide a name, intended question, input descriptions and result meaning. **Find existing parameter slots** proposes names and JSON types for supported value positions; confirm these suggestions. Large integers and decimals remain raw JSON. JSON Pointer bindings and constraints are under **Advanced bindings and constraints**. Add units, refund/cancellation rules, time boundaries, empty-result meaning and regression checks where relevant.
4. **Verify and publish.** Save the draft and run its example/checks against the real source. Read the row counts and outcomes. Open **Review and publish**. Publication atomically replaces the entire source semantic snapshot: other catalog, template or ontology-mapping changes are also shown and require acknowledgement. Failed trials, expired evidence or revision conflicts still block publication.
5. **Confirm client call.** Choose an authorized Agent or create one, open its client connection instructions and use `search_semantics` → `get_semantic_entry` → `execute_query_template`. Use the current execution version and appropriate parameters. The client panel follows three steps: connect an Agent, copy the tool call, and confirm the call. **Wait for client call** checks for matching evidence for up to two minutes; **Check now** performs one refresh. Waiting stops on navigation, a hidden tab, a closed panel, or changed query/access; no background monitor is created. The displayed request IDs refer to successful, non-preview query-Agent calls for this source, template, execution version and selected Agent in the last 30 days.

Under **Business context**, use **Business concepts** to link mapped concepts by name and inspect their definitions. You can also start from **Ontologies → Queries → Create query** to carry the selected source and concept into this flow. Associations become visible to Agents only after publication; they do not change the native query. See [concept-to-query workflows](ontologies.md#connect-concepts-to-queries).

**Save draft for later** persists the draft on the server. **Home → Continue last setup** and the query URL retain only stable references. Browser storage is scoped to the administrator; it contains no query text, parameter values, results or credentials. A query opened from an ontology can also carry ontology/concept IDs in its URL; browser resume storage remains source/template/Agent IDs only. Private browsing/storage restrictions may prevent the Home shortcut, but a saved query URL still works. Unsaved edits require saving or cancelling before navigation. After a save conflict, inspect the current server entry before explicitly merging your entry into the latest revision; other entries are preserved and the next save rechecks concurrency.

Existing queries use one editor from the query catalog, source Semantics and ontology views. Switch directly between **Query**, **Parameters** and **Business context**; each parameter keeps its example value beside its contract. Bindings, constraints and regression checks remain available under disclosures. **Save draft** does not publish. New queries retain the guided creation flow.

The workspace highlights the next action: run checks, review changes, set up a client or preview the published query. **Validation and versions** opens a side panel; **Agent client** expands the client setup and call evidence. Query details use the full workspace width. An unchanged, validated source has no active publish action. Publication still reviews the entire source draft.

Home keeps up to five recently opened queries per administrator, with the latest setup as the main resume action and a compact list for the others. Reopening a query moves it to the front. Home resolves the saved references against current server state and shows the query name and next step. A matching successful client call changes the shortcut to **Recent query**. Deleted queries offer **Choose another query**; deleted sources are not offered as resumable tasks. The source overview initially follows the same source. An unfinished setup is the primary action; otherwise, search is primary. Health attention rows show the cause and offer a direct check or the relevant repair page. Connection checks, health checks and query validation are labeled separately; a missing health check does not erase a successful connection check.

The workspace keeps these facts distinct:

| Dimension | Meaning |
| --- | --- |
| Publication | Draft, published, or unpublished changes; the contract panel shows the saved draft when one exists |
| Execution evidence | Whether the published query currently satisfies the existing execution checks; runtime authorization is checked again |
| Business acceptance | A separate human verdict on a specific question, data conditions and configuration; never inferred from query success |

Business reviews remain in source evaluations and are not automatically assigned to a template. Use **Business definitions and recovery → Review a business question** to record one. Historical calls, including calls made during client evaluations, do not prove current credentials work or that the answer was correct. Source-level counts include native queries; they cannot complete another template's setup. Missing activity means “not observed in this window,” not “never used.”

**Query tools → Available queries** lists executable published queries. Administrators also have **Drafts** (new, changed or pending removal) and **Needs attention** (enabled published queries blocked by validation or a disabled source). Selecting an Agent switches to published visibility and removes these management views; draft visibility is also blocked by the API. **All definitions** retains terms, metrics and visible ontology definitions. Executable search groups matches by data source and query, with related business definitions shown as context, so a concept and its query do not produce duplicate query cards. Clicking a query name opens its workspace directly; **Preview query** runs the published version in a separate preview. Opening a query and returning restores the search, source/Agent filters, page, position and selected result; browser Back follows the same snapshot. If publication or access changes invalidate the snapshot, restart the search. Management list pages also track draft revisions; saving a draft does not invalidate published-only catalog pages. **Operations** groups health and audit. Shared ontology management has its own **Ontologies** entry in the main navigation; connector documentation is under **Settings**; existing `/business`, `/ontologies`, `/audit`, `/catalog` and source URLs remain available.

Start with the [support queries demo](../examples/query-publishing/README.md). Use the [pilot worksheet](query-pilot.md) to measure actual setup time and business outcomes. No customer-efficiency or correctness improvement is claimed from these implementation checks.
