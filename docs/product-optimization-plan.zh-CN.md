# ContextGate 产品优化方案

日期：2026-09-16。代码基线：`89cf20d`，0.7.0。

本文保留最初建议及待验证假设。[English summary](product-optimization-plan.md)。

**0.8.0 实施状态：** 连续发布、草稿恢复、统一查询编辑、本体关联、真实客户端确认及简洁界面已交付，详见[发行说明](releases/0.8.0.zh-CN.md)。本体保留一级菜单；负责人字段、检索排序、外部目录导入、定时回归及真实客户试点仍为后续决策。下面的建议不能视为全部已实现，不修改现有授权、发布或部署契约。现状依据当前源码、产品文档和仓库中的验证记录；既有运行记录不等于本轮重新执行测试。当前没有客户访谈、留存或付费数据，目标客群、收益和工期均作为待验证假设。

**一、产品目标与取舍**

建议定位：**把企业已有的业务查询，发布成经过验证、可授权、可追溯的 Agent 工具。**

主价值是让经过确认的查询被持续复用，降低重复写查询、解释业务口径和审核 Agent 访问的成本。品牌继续使用 ContextGate；“语义数据网关”可以作为技术类别，首页、README 和演示首先说明具体任务、结果和适用人群。

优先客群：由一个数据或平台团队统一管理数据访问，已经有可用 SQL 或读取 API，并正在给内部 Agent 开放数据的组织。配置者是工程师或分析师，业务口径由领域负责人确认，使用者在已有 Agent 客户端完成任务，购买或部署决策者是平台负责人。这些是协作职责，不新增一套资源角色权限。

第一个试点场景建议选择内部客服查询订单、退款和处理状态。首轮以固定员工权限的数据范围和单数据源查询为主，优先 PostgreSQL 和现有固定 HTTP API；多源结果可以由外部 Agent 分别读取，但不承诺跨源身份归一、统一快照或联邦查询。客户直接使用、动态按终端用户隔离的场景，必须另行完成可信身份与数据库权限设计后才能纳入。

这一阶段保持已有原生查询路径，作为工程师探索入口；新建的“受控查询”流程推荐仅模板模式，由管理员明确选择。已有数据源模式保持原值。共享本体用于重复业务概念的统一定义，在有实际复用需求时引入。

暂停主动扩充连接器数量、复杂本体编辑能力和通用平台功能。保留并维护所有已有适配器与本体能力，不删除用户资产。新增连接器必须对应试点阻塞；预览连接器只有取得真实厂商环境证据后才能升级支持状态。

**二、将产品问题对应到具体改动**

| 当前问题 | 当前可复用能力 | 建议改动 | 判断效果的依据 |
| --- | --- | --- | --- |
| 首次配置路径长 | 原生预览、模板编辑、参数表单、配置 MCP | 从已有查询进入连续引导，保存进度和上下文 | 首次真实客户端成功调用所需时间、放弃位置 |
| 本体承诺容易超过能力 | 共享定义、固定版本映射 | 本体成为按需入口，明确其影响的是发现和解释 | 无本体也能完成主流程；复用前后维护工作量 |
| 工程师重复录入 | HTTP 操作生成模板、结构导入、条目编辑接口 | 原生查询转为模板草稿；导入差异审阅；复用业务说明 | 单个后续查询从录入到发布的人工耗时 |
| 调用成功不等于答案正确 | 回归断言、单次/对照评估、人工评审 | 分开报告运行状态和业务结论，建立固定问题集 | 已评审答案正确率、覆盖率、人工介入和端到端时间 |
| 发布后维护分散 | 发布历史、健康检查、影响分析、OTLP | 模板详情集中展示负责人、实际使用、验证与修复入口 | 发现问题到恢复的时间、每周维护投入 |
| 定位与购买理由模糊 | 自托管、多个 Agent、审计和受控执行 | 用一个真实场景展示跨 Agent 复用及维护收益 | 连续使用、第二个 Agent 复用、部署/付费意愿 |

不把已有功能重新列为新增交付。配置 MCP、HTTP API 模板生成、回归检查、业务目录、发布历史和实际客户端接入证据均属于优化基础。

**三、首次使用：从一条查询到一次真实业务调用**

默认入口为“发布一个查询”，同时提供“继续上次配置”。流程按任务组织，页面切换不要求重复选择数据源、模板和 Agent。

| 步骤 | 用户操作 | 系统工作与边界 | 完成条件 |
| --- | --- | --- | --- |
| 1. 选择来源 | 选择已有数据源，或新建连接并配置只读身份 | 复用连接检测，分别展示连通、引擎保护和账号权限证据 | 来源可用；未验证权限明确可见 |
| 2. 提供查询 | 粘贴已有原生查询及参数，复制当前预览，或选择固定 HTTP 操作 | 生成模板草稿；已有参数槽可自动列出，类型建议需确认 | 得到可编辑的草稿，不自动发布 |
| 3. 说明用途 | 填名称、用途、参数含义和结果说明 | 展示按参数类型生成的表单；业务术语和本体放在高级区 | Agent 有足够信息理解何时调用及结果含义 |
| 4. 验证与发布 | 执行样例，确认可观察结果，按需添加回归检查并审核 | 复用真实试跑、草稿修订、原子发布和失效机制 | 当前证据有效且管理员明确发布 |
| 5. 接入与确认 | 选择或创建 Agent，复制客户端配置，在真实客户端执行任务 | 展示当前权限和调用证据；保留请求 ID 与修复链接 | 出现对应 Agent、数据源、模板版本的非预览成功调用 |

涉及金额、统计口径或时间范围的查询，编辑界面提示补充币种/单位、退款与取消规则、时间区间及空结果含义。相关字段复用现有说明、单位、粒度、时间定义、注意事项和结果说明，不要求每条简单查询填写完整治理表单。

参数表单优先于 JSON Pointer；底层仍只绑定允许的现有参数槽。首版不把 SQL 字面量自动改成占位符，不自动推断金额或日期类型，不对查询做字符串插值。没有原生参数槽时给出对应查询族示例，由用户编辑。大整数和 Decimal 延续无损编码。

发布边界必须明确：现有发布单位是数据源语义快照。若引导过程中发现该源还包含其他草稿改动，进入完整变更审阅页，展示全部影响；不能将“发布当前查询”实现成静默发布其他人的草稿，也不为了向导新增独立模板发布系统。

继续配置通过数据源、草稿条目 ID 和服务端当前证据恢复。保存前执行原有修订检查；未保存编辑仍使用导航保护。不把数据库凭证、完整查询、参数或结果写入浏览器持久化缓存。首次验收要求关闭页面后能恢复已保存进度，冲突时能保留本地编辑并明确合并。

首页将“已发布”“已有客户端调用”“业务问题已验收”分别显示。某个模板的历史成功不代表当前全部模板、所有 Agent 或当前凭证均有效。

**四、信息架构与日常工作台**

最终导航为：首页、查询工具、数据源、本体、Agent、运维、设置。名称为产品呈现调整；“查询工具”复用现有查询模板与业务目录，不新增同义数据库实体。原有 URL 保持可访问，避免旧链接和工作流失效。

| 页面 | 默认展示 | 次级入口 |
| --- | --- | --- |
| 首页 | 继续配置、创建查询、需要处理的问题、近期真实调用 | 试点收益摘要，不展示没有行动价值的计数 |
| 查询工具 | 可执行查询、用途、数据源、状态、最近使用 | 详情中维护参数、回归、发布、业务定义和本体关联 |
| 数据源 | 连接状态、保护证据、可用查询、受影响 Agent | 原生结构探索、连接配置和高级限制 |
| Agent | 授权来源、到期、最近真实调用、连接配置 | OAuth 客户端管理 |
| 运维 | 连接/模板问题、变更影响、审计、恢复入口 | 健康策略、已有发布历史与导出 |
| 本体 | 共享定义、图形/列表编辑、版本与使用情况 | 从概念进入已关联查询或新建查询 |
| 设置 | 账号、语言、配置 MCP、部署设置 | 连接类型帮助 |

本体与完整业务定义仍可搜索、编辑和发布。图编辑器不再占据首次价值路径，其优先级由关联查询的实际使用驱动。

查询详情集中回答：能解决什么问题、输入什么、返回什么、谁负责、当前能否执行、业务结论由谁何时确认、哪些 Agent 有权使用、哪些 Agent 实际使用过、发生变更该如何恢复。授权清单和真实使用清单分别展示。

首页、查询详情和 Agent 接入页共用服务端就绪证据与前端状态转换函数。缓存状态附时间和范围；真正执行时由引擎重新验证，不把 UI 状态用作授权判断。

**五、发现、复用和语义能力**

先改善已有目录的可发现性：在已授权来源内按名称、别名、用途和适用问题匹配；可先增加确定性的精确匹配/前缀/包含匹配排序。仅在真实问题集证明检索失败后实施排序改动，不因“语义”二字直接引入向量数据库或模型服务。

可在条目中增加少量已确认的“适用问题示例”；沿用业务内容的加密存储。不要把验收标准、敏感示例参数或黄金答案发送给查询 Agent。所有业务描述仍是非可信数据，不能作为工具系统指令。

对名称近似、口径不同的查询，返回用途和差异，供 Agent 澄清选择。找不到合适模板时明确说明未覆盖；在仅模板模式下不自动回退到原生查询。查询响应提供已有数据源、模板和执行版本证据，以及截断/分页状态。执行时间不能标为数据新鲜度；只有上游明确提供且可解释的数据时点，才展示相应标注。

继续使用现有发现、目录读取和模板执行工具，不给每个模板默认注册独立 MCP 工具，不把整个目录一次性塞入上下文。发现接口仍遵守原有授权、分页与大小边界。排序变化必须保持稳定次序并绑定游标版本；相同权限和快照下翻页不能漏项或重复。

后续导入按需求推进：先支持已有原生查询、当前预览与固定 HTTP 操作；再考虑保存的模板包、选定 OpenAPI 操作或既有数据目录的导入。导入只生成可审阅草稿，显式绑定目标数据源，不能携带凭证、试跑证据或发布状态。导入对象数量有上限，按稳定 ID 显示新增/修改/冲突，不覆盖现有业务说明。

dbt 等集成只有在试点已经拥有对应资产且重复录入构成阻塞时实施。其目标是复用权威定义，不是维护两套未经同步的指标口径。

**六、维护成本与验证状态**

将三个状态维度分开，而不是用一个绿色“已验证”概括：

| 维度 | 状态示例 | 依据 |
| --- | --- | --- |
| 发布状态 | 草稿、已发布、有未发布改动 | 源语义修订与发布快照 |
| 执行证据 | 当前有效、需重新验证、当前不可执行 | 现有定义/连接/凭证/版本绑定与运行校验 |
| 业务验收 | 未评审、通过、部分通过、未通过、需复核 | 对明确问题、数据条件和版本的人工评审 |

业务验收不能替代执行授权；模板试跑通过不能自动变成业务验收通过。查询定义、参数契约、单位、时间口径和结果含义变化时，关联业务评审保留历史并标为需复核。名称或维护人变化不必触发查询执行版本变化。不要只依赖当前执行哈希判断业务含义是否改变，因为部分说明字段不会改变该哈希。

第一阶段集中现有健康与修复入口，第二阶段才按试点需要增加：

- 查询维护人：可选关联现有管理员，表示责任归属，不创造新的编辑权限。账号停用后保留历史归属并提示重新分配。
- 最近真实使用：从已脱敏审计按来源、模板和版本聚合，排除管理员预览和系统检查。说明审计窗口；没有记录标为“当前窗口内未观察到”，不能称为永久无人使用。
- 业务问题引用：将已保存评估问题关联模板，用于复核导航和证据展示，不能声称自动推断了完整依赖。
- 变更处理：连接/凭证变更保留当前失效机制，提供批量重新试跑与完整审阅入口；不自动恢复旧证据或自动发布。

周期性执行回归只在试点明确需要时增加，沿用现有后台工作器，不引入独立调度平台。管理员按模板选择启用、频率及预算；先覆盖小范围、无敏感测试值的查询。运行必须固定已发布快照和版本，不能拿当前草稿代替，也不能静默刷新发布验证证据。结果保存为独立运行检查记录。

周期检查遵守来源超时、并发及返回量限制，设置整轮预算，防止查询风暴和云端计费失控。运行检查失败首先形成带原因的运维问题；瞬时连接异常、返回值不符和执行证据失效分开处理。原有安全/版本失效继续阻止执行，单次业务断言失败不自动停用全部数据源。恢复仍经相应重试、人工复核和发布流程。

**七、业务效果评估**

第一轮直接复用现有单次和对照评估，不增加自动模型裁判。业务负责人先确定验收标准，评审者尽量不知道运行属于基线还是引导组。结果按问题报告，不只报一个汇总百分比。

建议每个试点收集 30 个真实问题：20 个用于配置与改进，10 个作为独立验收问题。包含常见问法、同义改写、时间/退款边界、空结果、无法回答和当前身份无权访问的情况。每题建议独立运行 3 次，以观察重复性；30 题是试点设计，不足以证明整个市场或所有问题类型的效果。

基线优先采用客户现有 Agent 工作流，固定模型版本、参数、数据条件和可访问范围；引导组增加经过发布的工具及业务说明。两组分别保存环境和配置元数据，不伪造“完全相同配置”。如果在现有同一来源对照模式下测试，仅改变会话指引，须记录实际工具调用；基线也使用语义模板时，不能归类为纯原生基线。

遇到两组需要不同查询模式/目录的实验，用等价权限的隔离配置与单次评估记录配对，并明确这是不同配置的试点实验；不绕过现有配置变化告警。数据应固定于专用样本或明确版本，无法固定的数据变化作为混杂因素报告，不仅依赖配置快照判断可比性。

首轮可在试点工作表补充端到端起止时间、人工介入次数、配置和维护工时。若反复人工记录构成阻塞，再给现有评估对象增加可选人工记录字段，并标注来源；不得把人工填报冒充服务器测量。Token 和模型费用仅在客户端提供可信 usage 时记录，否则显示缺失。

| 指标 | 定义与范围 | 建议试点门槛，非当前成绩 |
| --- | --- | --- |
| 首次查询激活时间 | 从开始创建查询到相应版本的首次真实客户端成功调用；报告总耗时与人工操作耗时 | 凭证、可运行查询和客户端已准备好时，中位数 ≤15 分钟 |
| 引导完成率 | 完成真实客户端调用的有效尝试 / 全部有效尝试；退出和失败计入 | ≥80%，先至少观察 10 次有效尝试 |
| 后续查询上线时间 | 第二条及以后查询从录入到发布的人工操作时间 | 中位数 ≤10 分钟，复杂业务另分组 |
| 工具选择正确率 | 在预先标注可用工具的题目中选择适用工具的运行 / 该组全部运行 | ≥90%；独立报告无法覆盖和歧义问题 |
| 业务答案正确率 | 正确运行 / 已完成且已评审运行；部分正确不并入正确 | 有效可回答问题 ≥90%；配对基线低于目标时期望提升 ≥15 个百分点 |
| 评审覆盖率 | 已评审运行 / 全部发起的有效运行 | ≥95%；同时列出未完成、失败、未评审，避免选择性报喜 |
| 端到端回答时间 | 客户端提问到最终回答，用同一种测量方式配对 | 在正确率不降低的前提下，中位数缩短 ≥30%，或人工介入下降 ≥50% |
| 持续复用 | 同一已发布查询被至少两个真实 Agent 在不同日期调用，排除测试与预览 | 每个试点出现至少一个这样的查询 |
| 维护收益 | 每周节省人工时间减去新增维护时间，初期配置成本单独累计 | 连续两周净收益为正；累计回本周期可计算 |
| 权限与只读边界 | 专门验收集中的越权、写入和旧凭证调用 | 已定义验收场景零绕过；不宣称覆盖所有攻击 |

高基线问题不能强求提升 15 个百分点；达到高正确率后重点考察省时、减少人工和维护成本。精确报告分母、样本量、模型和时间范围。不要将只有成功调用的审计作为所有用户问题的分母。

产品日常页面优先显示“真实业务问题的已评审完成数”、覆盖率及模板复用。缺少人工评审时显示运行指标，并明确缺少业务结论。维护工时和部署意愿在试点中先人工采集，不建设独立埋点或商业分析平台。

**八、权限、发布与运行边界**

保留 Agent → 数据源授权，以及数据库账号/视图负责表、字段、行权限的分工。模板参数属于查询输入，不是可信授权声明。首轮不增加每模板 ACL、多租户或通用策略引擎。

对同一数据库中的不同员工角色，使用现有不同权限的数据源配置；这会增加一些管理成本，应在试点记录，而不是声称已经完成终端用户权限透传。需要“当前客户只能查自己的订单”时，必须明确客户端用户身份从何而来、由谁校验、如何不可覆盖地进入授权，以及数据库如何限制范围，再单独设计。

配置 MCP 保持个人管理员身份与既有工具边界。可改进起始提示词和草稿创建体验，但不开放自动发布或 Agent 授权，不把配置 Token 当查询 Token 使用。连接修改立即生效的事实应在操作前展示。

现有加密、脱敏审计、版本绑定、撤销取消、无损编码、分页隔离与恢复约束继续作为验收条件。评估中的人工问题和验收标准沿用加密存储；不为了追踪收益默认保存生产查询结果、模型对话或参数明文。

部署先围绕当前单实例加强诊断、升级清单和备份恢复体验。主密钥与元数据库必须匹配持久化。高可用、SSO、资源隔离、终端用户身份绑定分别由具体部署阻塞触发，不能只靠加一个选项或多副本掩盖尚未实现的协调语义。

模型方面继续复用 `semantic.Entry`、`Template`、`State`、`Evidence`、`Evaluation`，不另建 Tool/Skill/Action/Workflow 等同义对象。名称、说明、注意事项、单位、粒度和结果说明已存在，先复用。新增适用问题、维护人或评估引用应有实际展示或行为用途。

业务评审可额外记录相关条目的业务内容摘要或修订证据，使语义变化能提示复核；这不改变原有执行版本算法，也不把过去评审删除。字段用途和归属在实现前固定，避免同时在模板和评估中维护两份真值。

兼容性要求：旧数据可读且不被自动补成“已验收”；旧 ID、HTTP/stdio/OAuth 行为和公开工具名保持稳定。新增字段按协议能力处理；旧客户端做整份草稿替换时，如果会丢失新字段，必须拒绝并说明升级或使用条目编辑，不能静默清空。不能因为字段可选就认为双向编辑天然兼容。确需格式版本升级时明确迁移、导入与回退边界。

新增只读管理摘要优先放在已有资源之下；只有界面确有重复聚合或需要新服务端事实时才增加端点。权限仍在后端执行，前端路由重组不改变身份边界。

**十、交付顺序与资源假设**

建议以里程碑交付，不同时启动所有功能。以下 6–8 周为“1 名后端、1 名前端、可持续参与的领域负责人，试点环境和只读凭证及时可用”的排期假设，不是已估算的开发承诺；人员与客户接入情况不同应重新排期。

| 阶段 | 建议时间窗 | 必须交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- |
| A：建立基线 | 第 1 周 | 场景与责任人、现有流程耗时、30 题初稿、首次路径交互稿、指标定义 | 有具体问题和可用样本，业务负责人愿意评审 |
| B：跑通首次价值 | 第 2–3 周 | 原生查询转模板、连续引导与恢复、完整发布审阅、真实调用确认、配套文档 | 至少 10 次有效尝试；权限与发布回归通过；记录激活时间与失败原因 |
| C：验证持续收益 | 第 4–5 周 | 查询目录/详情、版本与验收分层、最小使用摘要、问题集评估 | 能完成配对对照，出现跨 Agent 复用，知道主要维护成本在哪里 |
| D：试点与收敛 | 第 6–8 周 | 2–3 个独立使用团队的试点记录；只修复阻塞；按证据选择一个后续能力 | 连续两周观察真实使用和维护净收益，形成继续/调整决策 |

阶段 C/D 期间如有证据再选：目录排序、导入适配、周期回归、一个云连接器真实验证。每次只解决最主要的试点阻塞，不把这些全部列为首版必做。

后端负责查询和状态契约、权限、版本/发布不变量、服务端统计；前端负责连续路径、信息架构、参数与错误恢复；领域负责人负责口径、问题和盲评；产品负责人负责试点选择、指标解释与取舍。同一个人可兼任多个职责。

下一次功能发布以“查询发布与复用体验”为主题；具体版本号在实施和现有发布计划明确后决定，不在本方案擅自指定。

**十一、验收与发布策略**

按完整行为集中验证，复用现有测试文件和现有本机 Chrome 工具；不安装新的浏览器自动化框架。Linux 后端和数据库验证在 OrbStack 执行。文案与布局修改不新增字符串断言或仅确认旧入口消失的测试。

| 验收范围 | 必须观察到的行为 |
| --- | --- |
| 首次路径 | 原生查询和固定 HTTP 操作分别完成草稿、参数、试跑、审核、发布及真实客户端调用 |
| 参数语义 | 大整数/Decimal 不损失精度；可选参数省略保持原契约；绑定不能改命令、表名或查询结构 |
| 草稿与发布 | 已有其他草稿改动时显示完整差异；并发保存/发布冲突不覆盖他人；草稿变化不改变当前发布执行 |
| 权限与证据 | 错误 Agent、已撤销凭证、过期验证、仅模板模式的原生调用仍被拒绝；管理员预览不计真实接入 |
| 中断恢复 | 关闭/刷新后恢复已保存步骤；未保存内容有保护；失败重试前读取当前状态，避免重复提交 |
| 生命周期 | 连接变更、语义变更、回归失败分别显示正确状态；业务结论不会因仅执行成功变成正确 |
| 指标 | 未完成/未评审可见；试验与真实使用分开；分母、版本、时间范围准确；历史成功不冒充当前健康 |
| 兼容与恢复 | 0.7.0 配置升级和旧客户端行为按契约验证；发布历史、备份和匹配密钥恢复可用 |
| 前端 | 本机 Chrome 桌面/390px、中英文、键盘、空/加载/失败状态及实际导航；必要时检查控制台和网络 |

影响共享查询契约、参数绑定或权限路径时，除聚焦回归外，在候选发布执行覆盖所有受影响查询族的矩阵；如果改动会影响所有适配器，则执行现有完整矩阵。云连接器真实验证单列，模拟测试不能替代。生产构建与发行包检查按仓库既有门禁执行。

发布采用可回退的页面入口与明确的数据兼容策略，先在隔离试点实例验证。升级前备份元数据库及匹配主密钥；数据库发生向前迁移时，不能承诺仅替换旧二进制即可回退。旧导航/链接保留到兼容路径验证完成。

**十二、试点、商业验证与停止条件**

用脱敏示例提供可运行演示：客户订单查询、退款状态、明确时间口径的一项聚合。每个示例包含输入、业务说明、已有查询、回归条件、客户端问题和预期可观察行为。演示不强制先创建本体，也不把自动评分或全库理解作为卖点。

试点团队应已经有真实重复查询工作，而不是为了体验产品临时造需求。首轮由团队确认一个维护人和一个业务评审人，在原有客户端完成任务。访谈记录当前替代方案、维护投入、阻塞、持续使用意愿及可接受的部署/支持模式。

收益按“人工查询/解释/审核节省时间 − 新增维护时间”估算，标明人工填报来源；数据库/模型成本有可信记录才计入。商业上先验证对部署、升级和维护支持的需求及付费意愿，不在这一阶段新增计费系统，也不凭空设定价格。

决策规则：

- 如果首次配置时间过长，优先减少录入、上下文丢失和参数操作成本，暂缓其他功能。
- 如果执行稳定但答案没有改善，先检查业务契约、工具描述、检索和评估设计，不直接扩大本体。
- 如果正确率提升但维护净收益为负，减少需要维护的定义，优先复用已有资产；仍不改善就调整目标场景。
- 如果持续需求主要是原生数据库排障，允许定位收敛到受控查询网关，不强求所有用户使用语义和本体。
- 如果两个以上独立试点被同一企业能力阻塞，再为该能力单独立项；先区分真实购买前提与功能愿望。
- 如果试点不能出现持续使用、可复用查询或正维护收益，停止扩大平台范围，重新选择问题与用户。
